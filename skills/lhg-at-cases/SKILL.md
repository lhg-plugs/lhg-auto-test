# lhg-at-cases：三类测试用例设计法

> 目标：让"想测试用例"从凭感觉变成固定套路。
> 核心纪律：**正常 / 边界 / 异常三类缺一不可；每条预期结果必须可判定。**

## 1. 何时使用

- 有新功能要测，先设计用例表再写脚本 → 用本 skill
- 评审别人的测试计划："三类齐了吗" → 用第 4 节检查表
- 只想快速补用例 → 直接看第 3 节的边界/异常 elicitation 清单

## 2. 先澄清，再设计（最多问一轮）

动笔前必须搞清三件事，问一次问全：

1. **被测对象是什么**：API 接口 / 页面交互 / 纯函数逻辑？
2. **输入输出长什么样**：参数名、类型、正常返回值、错误时返回什么？
3. **谁在用**：登录用户 / 游客 / 管理员？（权限类异常用例依赖这个）

拿不准的输入输出标"待确认"，不许脑补编造。

## 3. 三类覆盖法

### 3.1 正常类（happy path）：2~3 条封顶

主流程走通即可。克制：不许把每种参数组合都列出来，那是组合爆炸的陷阱。

示例（登录接口）：
- TC-01：正确用户名+正确密码 → 200，返回 token 字段非空

### 3.2 边界类（boundary）：至少 2 条

边界是生产环境最爱炸的地方。按这张清单逐项过：

| 边界维度 | 提问 | 示例 |
|---|---|---|
| 空值 | 空字符串/空列表/空对象传进去会怎样？ | 用户名传 `""` |
| 临界值 | 刚好等于阈值、刚好超过 1 会怎样？ | 起送金额 30 元，传 30 和 29.99 |
| 超长 | 超过长度限制会怎样？截断还是报错？ | 备注 5000 字 |
| 特殊字符 | emoji、引号、换行、SQL 关键字会怎样？ | 昵称含 `'` 和 emoji |
| 类型边缘 | 0、负数、超大数、精度丢失会怎样？ | 数量传 0、-1、99999999 |
| 格式边缘 | 大小写、前后空格、全角半角会怎样？ | 邮箱前后带空格 |

### 3.3 异常类（error path）：至少 2 条

| 异常维度 | 提问 | 示例 |
|---|---|---|
| 错误输入 | 格式错、类型错、必填缺失会怎样？ | 手机号少一位 |
| 权限不足 | 没登录、权限不够会怎样？ | 游客调下单接口 → 401 |
| 依赖失败 | 数据库挂了、下游接口超时会怎样？ | 支付网关超时 → 明确错误码 |
| 资源不存在 | 查一个不存在的 ID 会怎样？ | 商品 ID 写错 → 404 |
| 重复操作 | 同样的请求发两遍会怎样？ | 重复下单是否幂等 |
| 并发冲突 | 两个人同时改同一条数据会怎样？ | （小白可先记下，长大再测） |

## 4. 用例表格式

| 编号 | 用例名 | 类型 | 前置条件 | 输入 | 预期结果 |
|---|---|---|---|---|---|
| TC-01 | 正确密码登录成功 | 正常 | 用户已注册 | user=boss, pw=正确 | 200，token 非空 |

编号规则：`TC-` + 两位序号，用例名 = "在测什么"一句话。

## 5. 可判定性标准（硬门）

每条用例的"预期结果"必须回答"怎么算过"，具体到以下至少一项：

- 状态码 / 错误码（如 200、401、400）
- 关键字段的值或形态（如 `token` 非空、`total == 200`）
- 用户可见的文案或状态（如"提示'用户名不能为空'"）

**不合格写法**（打回重写）：

- ❌ "正常显示" / "符合预期" / "成功" —— 空话
- ❌ "不报错" —— 没说对的是什么
- ✅ "返回 400，错误信息包含'手机号格式错误'"

## 6. 完整示例：从一句话到用例表

功能描述："做一个优惠券领取接口，每个用户每种券只能领一次。"

澄清后确认：接口 `POST /api/coupons/claim`，入参 `coupon_id`，出参成功 200 / 失败 4xx。

| 编号 | 用例名 | 类型 | 前置条件 | 输入 | 预期结果 |
|---|---|---|---|---|---|
| TC-01 | 正常领取优惠券 | 正常 | 用户已登录，券还有库存 | coupon_id=1001 | 200，返回券码 |
| TC-02 | 券领完时提示 | 边界 | 券库存只剩 1 张 | 两人同时领 | 一人 200，一人 400"已领完" |
| TC-03 | 重复领取被拒绝 | 异常 | 用户已领过该券 | coupon_id=1001 再领一次 | 400"每人限领一次" |
| TC-04 | 未登录领取被拒绝 | 异常 | 未登录 | coupon_id=1001 | 401 |
| TC-05 | 不存在的券 ID | 异常 | 用户已登录 | coupon_id=99999 | 404 |
| TC-06 | 空券 ID | 边界 | 用户已登录 | coupon_id="" | 400"参数错误" |

注意 TC-02：边界类不只看"值"的边界，也看"状态"的边界（库存临界）。

## 7. 用例评审 checklist（给别人挑毛病时用）

1. 三类齐了吗？缺类有没有写原因？
2. 随机抽 3 条，能说出"怎么算过"吗？
3. 有没有两条用例其实在测同一件事？（合并）
4. 有没有"不可能发生"的用例？（如"数据库被陨石击中"——删掉）
5. 异常类的预期结果是"明确的错误"还是"不报错"？（后者打回）
6. 用例数：小功能超过 10 条，砍到主干。

## 8. 按被测对象类型调整侧重

三类框架不变，但不同被测对象的"出题重点"不同：

**API 接口**：异常类是重点。状态码就是它的语言——每个异常用例都要写出期望状态码。
必问：没带 token 会怎样？token 过期呢？参数缺一个呢？Content-Type 错了呢？
幂等性单独列一条：同样的 POST 发两遍，是建两条还是返回已存在？

**页面交互**：边界类是重点。用户能乱点的、乱输的、乱跳的都是用例。
必问：按钮连点两下会怎样？输入框粘贴 5000 字会怎样？后退再前进表单还在吗？
网络断开时点提交，页面是卡死还是给提示？

**纯函数/逻辑**：边界类是重点，尤其是数值与类型边缘。
必问：传 0、负数、None 会怎样？列表为空呢？超大输入会不会慢到超时？
浮点数精度（如 0.1+0.2）有没有坑？

## 9. 反模式

1. **用例贪多**：小功能列 30 条用例，等于没重点。6~10 条封顶，抓主干。
2. **只测 happy path**：这是最常见的自欺欺人，生产事故 8 成来自边界和异常。
3. **预期结果抄需求原文**："按 PRD 显示"不算可判定，要写出具体值。
4. **跳过"待确认"**：输入输出没搞清就设计，脚本阶段全部返工。
5. **三类硬凑**：实在想不出边界/异常时，写"本功能暂无 X 类用例，原因：…"，比硬凑假用例诚实。

## 10. 与 superpowers / webapp-testing 的关系

- **superpowers** 管的是"流程纪律"（先写测试再写代码的 TDD 节奏、评审门）；本 skill 管的是"用例内容"（测什么、怎么才算测全）。两者互补：superpowers 告诉你"什么时候写测试"，lhg-at-cases 告诉你"写哪些测试"。
- **官方 webapp-testing** 是重型测试方法论（面向完整 Web 应用的质量体系）；本 skill 是"小白第一次写出能跑的测试"的入门套路。学完本 skill 再去看 webapp-testing，会顺得多。

## 11. 自检与反馈

每次执行完本 skill，做一次轻量自检：

1. 三类用例是否齐全？→ 缺类有没有写原因？
2. 每条预期结果是否可判定？→ 随机抽 3 条，能说出"怎么算过"吗？
3. 用例数是否克制？→ 小功能超过 10 条就砍。

标准冒烟用例：对"用户登录"功能输出用例表，检查正常/边界/异常三类齐全、每条预期结果可判定。

反馈渠道：以 `[QC] <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-auto-test/issues，正文写清"输入 → 错误输出 → 期望输出"。
