# lhg-at-quality：测试质量门

> 目标：把"测试写完了"变成可验证的结论，而不是感觉。
> 核心纪律：**先跑脚本（机器），再做评审（人）；blocker 不清零，不许说做完了。**

## 1. 何时使用

- 测试脚本写完、交付前 → 跑全流程
- 接手别人的测试代码 → 先跑第 2 步看体检结果
- 只想快速看一眼 → 只跑第 2 步（脚本），5 秒出结果

## 2. 第一步：跑确定性审计脚本（必做，零成本）

在项目根目录执行插件自带的脚本（用你所在平台执行本地脚本的方式）：

```
python3 <插件目录>/scripts/audit/test_audit.py --target <测试目录>
```

- 脚本输出 JSON（含每条发现的文件、行号、规则说明）与人类可读报告。
- 有 blocker 时脚本以非零 exit code 退出——这是设计，不是 bug。
- `--fail-on` 控制 exit code 语义：默认 `blocker`（供 hook/CI 用）；想更严可设为 `warning`。
- 脚本自动跳过 `node_modules/.git/coverage` 等目录。
- 脚本只做"机器可判定"的事：无断言、硬编码等待、硬编码密钥、TODO 残留等。它判定不了断言的业务正确性，那是第 4 步的事。

## 3. 第二步：分级

所有发现按三级处理：

| 级别 | 含义 | 处理 |
|---|---|---|
| blocker | 跑了也白跑 / 上线会出事 | 必须修，不接受豁免 |
| warning | 迟早会坑你 | 修掉，或写豁免理由+有效期 |
| nit | 顺手修掉更好 | 顺手修 |

blocker 清单（脚本自动检出）：

- **无断言的测试函数**：永远通过，等于没测
- **硬编码固定等待**（`time.sleep(5)` / `waitForTimeout`）：flaky 之源
- **硬编码密钥/密码**：测试代码也会进仓库
- **focused 测试**（`it.only` / `test.only`）：提交后 CI 只跑这一个

warning 清单（迟早会坑你）：

- 三类覆盖缺失（缺边界类 / 缺异常类）
- TODO/FIXME 残留、无理由的 skip
- 真实网络请求、未固定种子的随机、未冻结的时间
- 测试数据不清理、裸 except 吞异常、重试循环、绝对路径

## 4. 第三步：人工评审（脚本抓不到的）

抽查，不用全量，但每项都要有依据：

1. **断言强度**：随机抽 3 个测试，断言是否具体到值/状态码/字段？`assert result` 这类直接打回。
2. **三类覆盖**：整个测试目录正常/边界/异常是否齐全？缺类就列补用例建议。
3. **用例独立性**：挑 2~3 个测试单独运行，能过吗？（排除顺序依赖）
4. **业务正确性**：预期结果里的数值/状态码对照需求原文，是否真的对？不许脑补。
5. **可读性**：测试名能不能一眼看出在测什么？失败时好定位吗？

## 5. 第四步：输出报告

存为 `docs/test-audit-YYYYMMDD.md`，模板：

```
# 测试审计报告（YYYY-MM-DD）
- 目标：<测试目录>
- 脚本结果：blocker X / warning Y / nit Z（规则 24 条）
- blocker 处理：<逐条：已修复 / 需人工处理（原因）>
- warning 处理：<逐条：已修复 / 豁免（理由+有效期）>
- 人工评审：断言强度抽查 3/3 通过；三类覆盖：正常✓ 边界✓ 异常✓；
  独立运行抽查 2/2 通过；业务正确性对照需求原文无误
- 未执行项：<没跑过的测试，写"未执行"，不许写"通过">
- 结论：通过 / 不通过
```

## 6. warning 处理 cookbook（常见问题怎么修）

| warning | 典型场景 | 修法 |
|---|---|---|
| 缺边界类 | 只有 happy path | 按 lhg-at-cases 第 3.2 节清单补 2 条 |
| 缺异常类 | 没测过错误路径 | 按第 3.3 节清单补 2 条 |
| TODO 残留 | "以后再补" | 要么现在补，要么删掉并记录"为什么不测" |
| 无理由 skip | `@pytest.mark.skip` 裸奔 | 补 `reason="..."`，写清恢复条件 |
| 真实网络请求 | 单元测试调真实 API | 换成替身（mock）或移到集成测试目录 |
| 随机无种子 | `random.randint` 裸用 | 加 `random.seed(固定值)` |
| 时间未冻结 | `datetime.now()` | 用 freezegun 冻结，或把时间当参数传入 |
| 数据不清理 | 建了临时文件没删 | 用 fixture/teardown，用完即删 |
| 裸 except | `except: pass` | 改成 `pytest.raises(期望异常)` |
| 绝对路径 | `/home/xxx/...` | 换相对路径 / `tmp_path` / 环境变量 |

修不掉的（如"需要真实支付环境"）→ 列入"需人工处理"，写清原因和替代验证方式，
不许为清零改规则。

## 7. 测试失败时怎么读报告

测试红了别慌，按这个顺序看：

1. **看名字**：测试函数名就是用例名，先知道挂的是哪条用例。
2. **看断言行**：期望值 vs 实际值，差在哪？是代码 bug，还是用例写错了期望？
3. **单独跑它**：只跑这一个测试。能过 → 顺序依赖/数据污染，查隔离性；
   还是红 → 真问题。
4. **看最近改动**：这个测试上次绿是什么时候？之间改了什么？
5. **别急着改测试**：先问"是不是代码真的错了"。测试是 alarms，
   alarm 响了先查火情，不许为了消音拆 alarm（改测试迎合 bug 代码是作弊）。
6. **记录下来**：修完后把"原因→修法"记到团队的测试知识库，
   同样的坑不许第三次踩。

## 8. 反模式

1. **为清零改规则**：这是作弊。规则觉得严，提 issue 讨论，不许私下调阈值。
2. **"应该没问题"式评审**：人工评审每项都要有依据（脚本输出、单独运行结果、需求原文行号）。
3. **虚假通过**：有 blocker 就说"通过"，等于把炸弹埋给以后。
4. **只跑脚本不评审**：脚本抓不到"断言写错了值"这种业务问题，人必须看。

## 9. 审计频率与回归

- **每次写完测试**：只跑脚本（5 秒），blocker 当场修
- **每次提交**：hook 自动跑，有 blocker 会被拦截
- **交付前**：跑本 skill 全流程（含人工评审）
- **修完回归**：只跑脚本确认 blocker 消失，不用每次全量

## 10. 自检与反馈

每次执行完本 skill，做一次轻量自检：

1. 脚本是否真的跑了（而不是"我觉得没问题"）？→ 没跑不算做
2. blocker 是否清零或全部列入"需人工处理"？→ 有遗漏就补
3. 人工评审 5 项是否逐项有依据？→ "大概没问题"不算依据

标准冒烟用例：对插件自带的 `fixtures/` 跑脚本，确认坏 fixture 的 blocker 全命中、好 fixture 零 blocker（见仓库根 `smoke_test.py`）。

反馈渠道：以 `[QC] <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-auto-test/issues，正文写清"输入 → 错误输出 → 期望输出"。规则误报/漏报请附最小复现代码。
